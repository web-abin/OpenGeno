# OpenGeno / FeatTree — Doc Format Reference

This is the canonical specification of the feature tree document format. Every
skill in this library reads/writes documents according to this schema.

## Directory layout (in the host project)

```
<project-root>/
├── feat-tree/                  # Default location, configurable via .feat-tree.json
│   ├── index.md                # L1 root index — list of modules
│   ├── auth/
│   │   ├── index.md            # L2 module index
│   │   ├── login.md            # L3 feature doc
│   │   ├── signup.md
│   │   └── password-reset/     # Sub-module if a feature has multiple sub-features
│   │       ├── index.md
│   │       ├── request.md
│   │       └── confirm.md
│   ├── profile/
│   │   ├── index.md
│   │   └── ...
│   └── ...
└── .feat-tree.json             # Optional config (paths, drift mode, etc.)
```

Three tiers, each with a fixed schema:

| Tier | File | Purpose | Read by AI |
|------|------|---------|------------|
| L1 | `feat-tree/index.md` | Project module list, ~500 tokens | Always (mounted in CLAUDE.md) |
| L2 | `feat-tree/<module>/index.md` | Sub-feature list of a module | When task touches that module |
| L3 | `feat-tree/<module>/<feature>.md` | Detailed feature spec | When task touches that feature |

## L1 — Root Index

```markdown
---
type: og-root
schema: 1
last_synced_commit: <git-sha-or-empty>
---

# <Project> Feature Tree

Generated by OpenGeno. AI agents must read this index first to locate the
relevant feature documentation before changing user-visible behavior.

## Modules

| Module | Description | Path |
|--------|-------------|------|
| Auth | Login, signup, session, password reset | [auth/](auth/index.md) |
| Profile | View/edit user profile | [profile/](profile/index.md) |
| ... | ... | ... |

## Out of scope

The following are NOT documented in this tree (they're cross-cutting
infrastructure, not user-observable features):

- i18n / translations
- Analytics / telemetry
- Build tooling, CI/CD
- Error reporting (Sentry, etc.)
- Logging
- Pure utility helpers
```

## L2 — Module Index

```markdown
---
type: og-module
module: auth
schema: 1
last_synced_commit: <git-sha-or-empty>
---

# Auth

One-paragraph overview of what this module covers and what it does NOT cover.

## Features

| Feature | Kind | Path |
|---------|------|------|
| Login | UI | [login.md](login.md) |
| Signup | UI | [signup.md](signup.md) |
| Password Reset | UI (multi-screen) | [password-reset/](password-reset/index.md) |

## Cross-module dependencies

- `Profile` reads the user object that `Login` writes to `AuthState`.
- `Notifications` triggers password-reset flow on email link click.
```

## L3 — Feature Doc (UI)

```markdown
---
type: og-feature
kind: ui
feature: login
module: auth
schema: 1
code:
  - lib/features/auth/login_page.dart
  - lib/features/auth/login_controller.dart
  - lib/api/auth_service.dart
last_synced_commit: <git-sha>
last_reviewed: 2026-05-06
---

# Login

One-paragraph summary of what this feature is and why it exists.

## Wireframe

```
┌────────────────────────────┐
│ ← back                     │
│                            │
│   [logo]                   │
│   Sign in to <App>         │
│                            │
│   ┌──────────────────┐     │
│   │ email            │     │
│   └──────────────────┘     │
│   ┌──────────────────┐     │
│   │ password         │     │
│   └──────────────────┘     │
│   [ ] remember me          │
│                            │
│   [    Sign in    ]        │
│                            │
│   forgot password?         │
└────────────────────────────┘
```

ASCII or mermaid. Mermaid `flowchart` is preferred for state/flow diagrams.

## Entry points

How does the user arrive at this screen?

- Tap "Sign in" on landing page
- Deep link: `app://auth/login?redirect=...`
- Auto-redirect from any auth-required page

## Layout

Describe the structural composition. List sections top-to-bottom.

## Interactions

Numbered list of every interactive element with:
- Trigger (tap, type, swipe, etc.)
- Validation rules
- Visible feedback
- Resulting state change or navigation

## Logic

Business rules that aren't visible in the UI:
- API calls made (with paths and payload shape at high level)
- Storage writes (what gets persisted, how long)
- Side effects (events emitted, other modules notified)

## State

| State | Trigger | UI effect |
|-------|---------|-----------|
| idle | initial | empty form, button disabled |
| validating | typing | inline error if invalid |
| submitting | tap submit | spinner, fields disabled |
| error | API 401 | error toast, fields re-enabled |
| success | API 200 | navigate to redirect target |

## Animation

- Sign in button: scale 1.0 → 0.95 on press, 100ms
- Error toast: slide-down 200ms ease-out
- Page transition: standard platform push

## Cross-feature links

- → [Password Reset](password-reset/index.md) (forgot password link)
- → [Session Refresh](session-refresh.md) (after successful login)
- ← [Landing](../onboarding/landing.md) (entry point)

## Edge cases

- Network offline → show offline banner, disable submit
- Email already used → suggest sign in with different account
- Account locked → redirect to [Account Recovery](account-recovery.md)

## Related code

- `lib/features/auth/login_page.dart` — UI tree
- `lib/features/auth/login_controller.dart` — state machine
- `lib/api/auth_service.dart` — network layer
```

## L3 — Feature Doc (Logic / non-UI)

Same frontmatter but `kind: logic`. Sections differ:

```markdown
---
type: og-feature
kind: logic
feature: session-refresh
module: auth
schema: 1
code:
  - lib/auth/session_refresh.dart
  - lib/api/auth_service.dart
last_synced_commit: <git-sha>
last_reviewed: 2026-05-06
---

# Session Refresh

One-paragraph summary.

## Triggers

When does this run?
- Token < 5 min until expiry → scheduled refresh
- App returns to foreground after backgrounded > 30 min
- Manual refresh via `AuthState.refresh()`

## Inputs

What data does it consume?
- Current `refresh_token` from `TokenStorage`
- Optional `force` flag

## Outputs

What does it produce?
- New `access_token` (15 min lifetime)
- Rotated `refresh_token` (30 day lifetime)
- On failure: emits `auth-expired` event

## Logic flow

Numbered or mermaid flowchart of the steps.

## State

If the logic has internal state machine, document transitions.

## Failure modes

| Failure | Detection | Recovery |
|---------|-----------|----------|
| Refresh token expired | API 401 | Emit auth-expired, force logout |
| Network error | timeout | Backoff retry up to 3x, then auth-expired |
| Server 5xx | API 500 | Same as network error |

## Cross-feature links

- ← [Login](login.md) — initial token issuance
- → [Logout](logout.md) — failure path

## Related code

- `lib/auth/session_refresh.dart`
```

## Frontmatter field reference

| Field | Required | Description |
|-------|----------|-------------|
| `type` | yes | `og-root`, `og-module`, or `og-feature` |
| `schema` | yes | Schema version, currently `1` |
| `kind` | features only | `ui` or `logic` |
| `feature` | features only | Feature slug (kebab-case) |
| `module` | features+modules | Module slug |
| `code` | features only | List of source file paths this doc describes |
| `last_synced_commit` | yes | Git SHA at which doc was last verified against code. Empty string if never synced. |
| `last_reviewed` | features only | ISO date of last human review |

## Drift detection contract

A doc is considered **in drift** if:

1. Any file in `code:` has been modified since `last_synced_commit`, AND
2. The modification was not a pure-refactor / pure-formatting change

The drift-check script reports candidates; humans/AI confirm whether each is
actual drift or noise.

`last_synced_commit: ""` (empty) means the doc has never been synced — it's
either a freshly-stubbed file or a placeholder. The drift checker treats this
as "needs initial sync" rather than drift.

## `.feat-tree.json` schema

Project-root config file written by `/geno-init` and read by hooks /
`/geno-sync`:

| Field | Values | Read by |
|-------|--------|---------|
| `version` | integer (currently `1`) | All consumers |
| `tree_path` | path string, default `"feat-tree"` | `drift-check.sh` |
| `drift_mode` | `"warn"` \| `"block"` | `stop-check.sh` |
| `gen_mode` | `"stub"` \| `"full"` | `/geno-sync` (to distinguish unwritten stubs from unverified full-mode prose) |

## Writing rules

These rules apply to AI agents writing or updating docs:

1. **One feature = one L3 doc.** Don't merge multiple features into one file
   "for convenience." If two features always change together, that's a hint
   they should be one feature in the tree.

2. **Describe behavior, not implementation.** Avoid pseudocode that mirrors
   actual code structure. Code is the source of truth for *how*; docs are
   the source of truth for *what* and *why*.

3. **Wireframes for every UI feature.** Even rough ASCII art. The wireframe
   anchors the rest of the doc.

4. **Cross-links are one-way assertions.** A doc says "I depend on X" — it
   does not promise X agrees. The drift check does not enforce reciprocity;
   it's the author's job to keep cross-links consistent.

5. **Limit cross-link depth.** When reading a doc, follow at most one hop of
   cross-links by default. Going deeper requires explicit AI judgment that
   the deeper context is needed.

6. **Update `last_synced_commit` only when verified.** Bumping the SHA
   without actually re-reading code is the failure mode that destroys this
   system. If unsure, leave the SHA stale and let drift-check flag it.

7. **No code dumps.** Don't paste blocks of source code into docs.
   Reference files in the `code:` frontmatter and the `Related code`
   section instead.
